# Knowloop MVP 데모 스크립트

## 1. 문서 목적

이 문서는 Knowloop MVP를 어떤 순서와 메시지로 시연할지 정리한 데모 스크립트 문서다.

이 문서의 목적은 다음과 같다.

- 발표와 시연의 흐름을 고정한다
- 무엇을 먼저 보여주고 무엇을 나중에 보여줄지 정한다
- 구현 우선순위가 데모 가치와 어긋나지 않게 만든다
- 시연 중 강조해야 할 핵심 메시지를 통일한다

---

## 2. 데모의 핵심 목표

이번 데모는 아래 한 문장을 증명해야 한다.

`Knowloop는 질문에 답하는 채팅앱이 아니라, 학생 질문을 학습 자산과 공식 지식으로 축적하는 교육용 Memory Workflow 앱이다.`

즉, 데모에서 반드시 보여야 하는 것은 다음 4가지다.

1. 학생 질문이 저장된다
2. 질문이 learning layer와 candidate로 구조화된다
3. 교강사가 반복 질문과 오개념 후보를 본다
4. 교강사 승인으로 formal wiki가 갱신된다

---

## 3. 데모 시간 가이드

권장 시연 시간:

- 짧은 발표용: 3~4분
- 일반 데모용: 5~7분
- 여유 있는 질의응답 포함: 8~10분

가장 이상적인 기준은 5분 안에 핵심 흐름을 다 보여주는 것이다.

---

## 4. 데모의 주인공

이번 데모의 중심 역할은 다음 두 사용자다.

1. `수강생`
2. `교강사`

운영자 역할은 이번 MVP 데모의 주인공이 아니다.

운영 기능은 필요하면 “이 구조는 운영 영역으로도 확장 가능하다” 정도로 짧게 언급한다.

---

## 5. 데모 전에 준비해야 할 fixture

## 5.1 과목 fixture

- 강의자료 1개 이상
- 과목 개념 wiki 1개 이상
- FAQ 또는 misconception 예시 1개 이상

## 5.2 학생 fixture

- 학생 1명의 학습 기록
- 유사 질문 3개 이상
- misconception 후보가 생길 만한 질문 세트

## 5.3 교강사 fixture

- candidate 검토 대기 항목
- approve 예시 1개
- merge 예시 1개 또는 drop 예시 1개

## 5.4 데모에서 실제로 필요한 화면

- 학생 질문 화면
- 학생 학습 허브
- 교강사 인사이트 대시보드
- candidate review inbox
- course wiki explorer

---

## 6. 권장 화면 순서

데모는 아래 순서로 진행하는 것이 가장 설득력 있다.

1. Student 질문 화면
2. Student Learning Hub
3. Instructor Insight Dashboard
4. Candidate Review Inbox
5. Course Wiki Explorer
6. 재질문을 통한 반영 확인

이 순서는 `입력 -> 축적 -> 검토 -> 승격 -> 재사용` 흐름과 일치한다.

---

## 7. 메인 데모 시나리오

## Stage 1. 문제 제시

### 보여줄 것

- 학생이 개념 질문을 한다
- 일반 챗봇이라면 답변하고 끝났을 장면임을 짧게 언급한다

### 말할 포인트

- “보통 AI 학습은 이 질문응답이 채팅창에서 끝납니다.”
- “Knowloop는 이 질문을 답변으로 끝내지 않고 학습 자산으로 이어지게 합니다.”

### 화면 포인트

- 채팅창만 꽉 차지 않게 한다
- 옆 패널 또는 보조 영역에 `session saved`, `candidate generated`, `learning updated` 같은 변화가 보이면 좋다

---

## Stage 2. 학생 질문과 답변

### 보여줄 것

- 학생이 질문 입력
- 시스템이 course wiki와 최근 session context를 참고해 답변

### 말할 포인트

- “이 답변은 단순히 LLM이 즉석 생성한 문장이 아니라, 기존 학습 맥락과 위키를 참조한 결과입니다.”
- “Knowloop의 핵심은 이 다음 단계입니다.”

### 꼭 확인할 것

- 질문/답변이 session memory에 저장되었다는 신호
- source 또는 retrieval trace가 보이면 더 좋음

---

## Stage 3. Student Learning Hub 전환

### 보여줄 것

- 방금 질문 이후 학생 허브에서 갱신된 항목
- notes
- gaps
- next actions

### 말할 포인트

- “Knowloop는 답변만 하지 않고 학생 개인 learning layer를 갱신합니다.”
- “그래서 배움이 휘발되지 않고 다음 학습 행동으로 이어집니다.”

### 꼭 보여줄 것

- 새로 추가된 약점 개념
- 다음 학습 액션
- 최근 학습 메모

---

## Stage 4. Instructor Insight Dashboard 전환

### 보여줄 것

- 반복 질문 집계
- 오개념 후보
- 어떤 개념에서 많이 막히는지

### 말할 포인트

- “학생 한 명의 질문은 개인 기록으로 끝나지 않고, 반 단위 학습 신호로 집계됩니다.”
- “교강사는 누가 뭘 물었는지 전부 읽는 대신, 수업 개입에 필요한 구조화된 인사이트를 봅니다.”

### 꼭 보여줄 것

- 같은 유형 질문이 묶인 candidate
- misconception 또는 FAQ 후보

---

## Stage 5. Candidate Review Inbox

### 보여줄 것

- candidate 상세
- summary
- confidence
- source refs
- approve / merge / drop 액션

### 말할 포인트

- “Knowloop는 AI가 바로 wiki를 쓰지 않습니다.”
- “반드시 candidate 단계에서 검토하고 승인합니다.”
- “이 단계가 교육용 시스템으로서 신뢰도를 지키는 핵심입니다.”

### 꼭 보여줄 것

- approve 또는 merge 중 하나의 실제 동작
- 상태가 `open -> promoted` 또는 `open -> merged`로 바뀌는 장면

---

## Stage 6. Course Wiki Explorer

### 보여줄 것

- formal wiki 페이지
- 방금 승인된 항목 반영 결과
- source trace

### 말할 포인트

- “이제 이 내용은 임시 답변이 아니라 공식 knowledge layer에 반영되었습니다.”
- “Knowloop의 본체는 채팅이 아니라 이 살아있는 위키입니다.”

### 꼭 보여줄 것

- 반영 전보다 정리된 FAQ 또는 misconception page
- source refs 또는 candidate refs

---

## Stage 7. 재질문으로 반영 확인

### 보여줄 것

- 유사 질문을 다시 입력
- 시스템이 갱신된 wiki를 바탕으로 더 구조화된 답변을 제공

### 말할 포인트

- “한 번의 질문이 끝나지 않고 다음 답변 품질로 이어집니다.”
- “이것이 Knowloop가 챗봇이 아니라 Memory Workflow 앱인 이유입니다.”

### 꼭 보여줄 것

- 최신 wiki가 참조되었다는 점
- 승격 이전보다 더 일관된 답변

---

## 8. 발표용 한 줄 메시지

각 단계에서 아래 문장을 중심으로 설명하면 좋다.

### 시작
- “Knowloop는 교육용 챗봇이 아니라, 질문을 학습 자산으로 바꾸는 시스템입니다.”

### 학생 질문 직후
- “질문은 session memory에 저장되고, 학습 레이어와 후보 지식으로 다시 구조화됩니다.”

### 교강사 화면
- “교강사는 개별 채팅을 다 읽지 않아도, 반복 질문과 오개념 패턴을 구조적으로 볼 수 있습니다.”

### 검토 화면
- “AI가 직접 공식 위키를 쓰지 않고, 후보 단계와 승인 단계를 거칩니다.”

### 위키 반영 후
- “이제 축적된 지식이 다음 학생의 답변 품질을 높입니다.”

---

## 9. 데모 중 절대 놓치면 안 되는 장면

아래 장면은 하나라도 빠지면 Knowloop의 정체성이 약해진다.

1. 질문 저장 확인
2. learning layer 갱신 확인
3. candidate 생성 확인
4. 교강사 승인 액션
5. formal wiki 반영 결과

즉, 채팅 답변만 잘 나오는 장면은 데모의 핵심이 아니다.

---

## 10. 데모 중 생략해도 되는 것

시간이 부족하면 아래는 짧게 말로만 처리할 수 있다.

- 운영자 확장 가능성
- 고급 audit 상세 화면
- flashcards
- graph visualization
- hybrid search 확장 계획

이것들은 방향성 설명용 요소이지, MVP 핵심 증명 장면은 아니다.

---

## 11. 추천 데모 시간 배분

5분 기준:

1. 문제 소개: 30초
2. 학생 질문/답변: 60초
3. 학생 학습 허브: 45초
4. 교강사 대시보드: 45초
5. candidate 검토: 60초
6. wiki 반영 확인: 30초
7. 재질문 및 결론: 30초

---

## 12. 실패했을 때의 fallback 시연

데모 중 일부 자동 흐름이 불안정하면 아래 fallback을 준비한다.

### fallback A. candidate 사전 생성
- 반복 질문 candidate를 미리 fixture로 준비
- 실시간 생성이 흔들리면 검토 흐름부터 보여준다

### fallback B. wiki 반영 전후 페이지 준비
- 승인 후 반영 결과를 즉시 보여주기 어렵다면
- 반영 전/후 상태를 준비해 비교 시연한다

### fallback C. learning layer 사전 생성
- gaps / next actions가 실시간으로 흔들리면
- 직전 실행 결과를 안정적으로 보여준다

원칙:
- fallback을 쓰더라도 흐름의 논리는 유지해야 한다
- “질문 -> 축적 -> 검토 -> 승격” 구조만 무너지지 않으면 된다

---

## 13. 데모 종료 멘트

마무리는 아래 메시지로 정리하면 좋다.

`Knowloop는 답변을 잘하는 AI를 하나 더 만드는 것이 아니라, 학생 질문이 사라지지 않고 학습 자산과 공식 지식으로 이어지도록 만드는 교육용 Memory Workflow를 구현합니다.`

---

## 14. 구현 우선순위와의 연결

이 데모 스크립트 기준으로 구현 우선순위는 다음과 같이 정리된다.

1. 학생 질문/답변 저장
2. learning layer 생성
3. candidate 생성
4. 교강사 candidate 조회
5. approve / merge / drop
6. wiki 반영
7. 재질문 시 반영 확인

즉, 이 문서는 발표용 문서이면서 동시에 MVP 개발 우선순위 문서다.

---

## 15. 한 줄 결론

Knowloop 데모는 `채팅을 보여주는 데모`가 아니라,
`학생 질문이 학습 자산과 공식 위키로 이어지는 과정을 시각적으로 증명하는 데모`로 설계해야 한다.
